# API Migration Plan

This document inventories the current Spring Boot API, how the Next.js frontend uses it, and a proposed target shape for moving backend behavior into Next.js/TypeScript while keeping Vercel, Neon PostgreSQL, and Clerk.

## Implementation Status

Implemented on `codex/api-migration-plan` on August 31, 2026:

- Added the transaction-aware PostgreSQL layer in `frontend/src/server/db` using `pg`.
- Consolidated Clerk, persisted guest, pending guest, and anonymous session resolution under `frontend/src/server/auth`.
- Moved guest creation and transactional guest-to-Clerk migration to Next route handlers.
- Ported course lookup/sync, academic overview, planner mutations, Gen Ed assignment, UL concentration, profile metadata, onboarding, and admin catalog behavior to TypeScript services.
- Added the versionless route handlers listed in the target API shape.
- Cut browser and server callers over to the Next services and removed the Spring proxy.
- Replaced the Spring warm-up ping with `GET /api/health`.
- Updated Docker Compose so the normal local stack runs PostgreSQL and Next.js without Spring.
- Added executable Gen Ed parity tests and verified a production frontend build.

The endpoint inventory below is retained as a record of the pre-migration Spring contract. The Spring source remains in `backend/` as a rollback/reference implementation, but the frontend no longer calls it.

## Deployment Requirements

- Set `DATABASE_URL` in Vercel to the Neon pooled PostgreSQL connection string.
- Optionally set `DATABASE_POOL_MAX`; it defaults to `5` per Next.js process.
- Keep the existing Clerk variables and guest cookie variables.
- Remove `NEXT_PUBLIC_API_URL`, `API_BASE_URL`, and `DOCKER_API_URL` after deployment configuration is updated; the application no longer reads them.
- Apply the reviewed, non-destructive compatibility migration at `docs/migrations/2026-08-31-next-api-compatibility.sql` before deployment.
- Run live smoke tests against a database clone before directing production traffic to the Next routes.

## Shared Database Schema

The TypeScript services intentionally use the schema already managed by Spring/JPA. No destructive migration is generated by this change.

| Table | Important columns | Ownership and relationships |
| --- | --- | --- |
| `users` | `id`, `ul_concentration`, `start_term`, `start_year`, `end_term`, `end_year`, `major`, `minor`, `note`, `track`, guest lifecycle columns | Clerk ids and `guest_*` ids share this table. `track` keeps the existing Java enum ordinal mapping. |
| `courses` | `course_id`, `name`, `dept_id`, `credits`, `gen_eds`, `last_synced_at` | Course catalog cache. `gen_eds` remains JSON text for compatibility with the JPA converter. |
| `user_courses` | `id`, `user_id`, `course_id`, `term`, `year`, `selected_gen_eds`, `transfer_credit_name`, `custom_ul_concentration`, `transfer_gen_eds_override`, `index` | Planner placements. `course_id` is a foreign key into shared `courses`; `user_id` is a foreign key into `users`. `selected_gen_eds` is a persisted derived assignment cache used by course DTOs and refreshed after planner mutations. |
| `user_off_semesters` | `user_id`, `term`, `year` | Element collection owned by `users`. |
| `user_completed_semesters` | `user_id`, `term`, `year` | Element collection owned by `users`. |
| `guest_sessions` | `id`, `token_hash`, `user_id`, timestamps, invalidation/migration columns | Stores only SHA-256 token hashes. Indexed by unique `token_hash` and by `user_id`. |
| `guest_usage_stats` | `stat_date` and lifecycle counters | Daily guest lifecycle metrics updated transactionally. |

## Goals

- Move the app toward one TypeScript codebase hosted primarily on Vercel.
- Keep Neon PostgreSQL as the source of truth.
- Keep Clerk authentication.
- Preserve the current planner, audit, onboarding, guest-session, and admin workflows during migration.
- Use DTO-shaped responses at API boundaries. Do not expose database models directly.
- Reduce endpoint sprawl where the frontend already wants aggregate data after a write.

## Current Architecture

- Frontend lives in `frontend/` and uses Next.js 15, React, TypeScript, Tailwind, Clerk, and server actions.
- Backend lives in `backend/` and uses Spring Boot 3, Java 21, Spring Security, Spring Data JPA, and PostgreSQL.
- Local database runs through Docker Compose. Production database is Neon.
- Course catalog data comes from the `umd.io` API and is cached/persisted by the backend course service.
- Most user-facing frontend calls go through `frontend/src/lib/api/planner/planner.client.ts` or `frontend/src/lib/api/planner/planner.server.ts`.
- Server-rendered frontend code calls Spring through `frontend/src/lib/api/server.ts`.
- Browser code uses `frontend/src/hooks/useFetchWithAuthClient.ts`.
- Guest browser requests without a Clerk token go through the Next proxy route at `frontend/src/app/api/backend/[...route]/route.ts`; Clerk-authenticated browser requests call `NEXT_PUBLIC_API_URL` directly.

## Current Auth And Request Flow

Authenticated users:

- Clerk issues a JWT.
- Frontend attaches `Authorization: Bearer <token>`.
- Spring Security validates the Clerk JWKS configured by `clerk.jwks-url`.
- `AuthUtils.getCurrentUserId(authentication)` resolves the app user id from the security principal.

Guest users:

- `POST /api/auth/guest` is a Next route, not a Spring route.
- It creates a pending local guest cookie before a real backend guest user exists.
- Server reads pending guest state from `frontend/src/lib/api/auth/guest-session.ts`.
- After onboarding data is submitted, `clearPendingGuestMarker()` removes the pending marker.
- Spring also supports real guest sessions with `POST /api/v1/auth/guest`, guest cookies, `GuestAuthenticationFilter`, and `GuestSessionService`.

Migration note:

- The current guest flow is split between Next and Spring. This should become one Next-owned flow so pending guests, persisted guests, and guest-to-Clerk migration are handled by the same session module.

## Response Shape Recommendation

Use one consistent response envelope:

```ts
type ApiResult<T> =
  | { ok: true; data: T; message?: string }
  | { ok: false; error: { code: string; message: string; details?: unknown } };
```

Why:

- The frontend already converts Spring responses into `CustomServerResponse`.
- `ok` maps directly to fetch success logic.
- Structured `error.code` is easier to handle than string matching `message`.
- `data` can stay DTO-only.

For write endpoints that affect derived state, prefer:

```ts
type PlannerMutationResult = {
  changedCourses?: CourseWithSemester[];
  deletedCount?: number;
  derived?: {
    genEdRequirements: GenEdRequirement[];
    upperLevelConcentration: ULConcentration;
  };
};
```

This replaces the current split between `/usercourses` and `/usercourses/with-updates` without forcing every caller to refresh the full page aggregate.

## Database And Transaction Notes

The risky backend operations are not the simple reads. The risky operations are writes that update multiple concepts:

- onboarding replaces transfer credits and updates user profile
- guest migration moves data from one user id to another
- course add/delete recalculates Gen Ed requirements and UL concentration state
- off-term deletion may affect visible planner structure

When porting these, preserve transaction boundaries. In Spring, service methods may rely on repository behavior and JPA transaction semantics. In Next, make transaction handling explicit in the data-access layer.

Do not generate destructive migrations automatically. First document the current schema, then choose a migration tool and only create reviewed migrations.

## gRPC Recommendation

Do not start the migration with gRPC.

For this app, REST-style Next route handlers plus shared TypeScript DTOs are a better fit because:

- the main consumers are browser and server components in the same Next app
- Vercel serverless routing fits HTTP JSON routes naturally
- Clerk and cookie session behavior are simpler with route handlers
- most current endpoints are CRUD or aggregate read models
- avoiding gRPC keeps local development and deployment simpler

If stronger contracts become necessary later, add generated OpenAPI types or a lightweight typed client after the route shape stabilizes. Consider gRPC only if a separate long-lived backend service remains and multiple non-browser clients need strongly typed RPC.

## Migration Order

1. Stabilize the current contract.
   - Keep Spring running.
   - Add this endpoint inventory to the repo.
   - Add DTO/type definitions for the current frontend contract.
   - Add smoke tests around the highest-value flows: session, academic overview, onboarding submit, add course, delete course.

2. Move session resolution first.
   - Replace `GET /api/v1/auth/session` with a Next-owned `GET /api/session` or server helper.
   - Consolidate pending guest and persisted guest behavior.
   - Keep cookie names and expiration behavior compatible during the cutover.

3. Move read-only course endpoints.
   - Port course lookup and autocomplete.
   - Keep `umd.io` fetch behavior behind `course-service.ts`.
   - Verify admin catalog export still uses DTOs.

4. Move academic overview.
   - Port `AcademicInfoController.getAcademicOverview`.
   - Match the existing frontend shape first.
   - After parity, rename fields from Java-style names to the frontend's final names.

5. Move planner mutations.
   - Port course save/delete.
   - Replace `/with-updates` with a single mutation result that can include derived data.
   - Verify planner row add/remove updates Gen Ed and UL state without extra refresh bugs.

6. Move user profile and planner metadata.
   - Port notes, semester completion, off-terms, and CS track update.
   - Fold redundant read endpoints into academic overview where practical.

7. Move onboarding.
   - Port onboarding read/write after user/course services are stable.
   - Make transfer-credit replacement transactional.
   - Keep transcript parsing as-is because it already runs in Next.

8. Move admin tools.
   - Port course sync and catalog export.
   - Keep role checks equivalent to Spring `hasRole('ADMIN')`.

9. Retire the Spring proxy.
   - Remove `/api/backend/[...route]` after all Spring calls are gone.
   - Remove `NEXT_PUBLIC_API_URL` usage where it only exists for Spring.
   - Keep only the environment variables needed by Next, Clerk, Neon, cookies, and `umd.io`.

## Starting Implementation Plan

Use this as the first branch-sized plan before porting major business logic.

1. Add a TypeScript backend foundation in `frontend/src/server`.
   - Create folders for `auth`, `db`, `dto`, `services`, and `validation`.
   - Keep route handlers thin and put real behavior in service modules.
   - Reuse the existing frontend Zod schemas where they already match API contracts.

2. Choose and configure the Neon data-access layer.
   - Pick the smallest practical option for Next route handlers.
   - Add a single shared database client module.
   - Add explicit transaction helpers before moving onboarding or guest migration.
   - Do not create destructive migrations automatically.

3. Document the current database schema.
   - Capture tables, columns, relationships, constraints, and indexes from the current Spring/JPA model and database.
   - Note any implicit JPA behavior that TypeScript code will need to reproduce.
   - Identify whether existing IDs are Clerk user IDs, guest user IDs, or generated database IDs.

4. Define shared API result helpers.
   - Add one `ApiResult<T>` response shape.
   - Add helpers for success responses, validation errors, unauthorized errors, forbidden errors, and unexpected errors.
   - Update new routes to use the new envelope while old Spring proxy routes continue using the wrapper conversion.

5. Port session resolution first.
   - Build `getCurrentSession()` in `frontend/src/server/auth`.
   - Support Clerk users, persisted guests, pending guests, and anonymous users.
   - Add a Next route or server-only helper for the current session.
   - Keep existing cookie names so current users are not forced through setup again.

6. Port guest-session creation and migration.
   - Replace the split pending/Spring guest behavior with one Next-owned service.
   - Create or resume guest users in Neon.
   - Make guest-to-Clerk migration transactional.
   - Preserve guest cookie deletion on successful migration.

7. Port read-only course lookup next.
   - Implement course autocomplete.
   - Implement course lookup by course id.
   - Keep `umd.io` access isolated behind a course service.
   - Decide and document whether course lookup is allowed to write missing courses to the database.

8. Add parity tests around the first migrated slice.
   - Test session resolution for anonymous, Clerk, pending guest, and persisted guest states.
   - Test guest creation/resume behavior.
   - Test guest migration data ownership changes.
   - Test course autocomplete and course lookup against mocked `umd.io` responses.

9. Cut over frontend callers one route group at a time.
   - Start with session and guest routes.
   - Then move course lookup/autocomplete.
   - Keep the Spring proxy in place until each caller for a route group is gone.
   - After each cutover, run the affected page manually and remove only the now-dead wrapper code.

## Current Cleanup Opportunities

- Standardize endpoint namespaces. Today the app mixes `/api/v1/*`, `/api/courses/*`, `/api/admin/courses/*`, `/api/public/ping`, and Next-local `/api/auth/guest`.
- Return updated UL concentration from `PATCH /ulconcentration`; the frontend currently receives only the selected concentration string.
- Fix response consistency. Spring returns `{ status, data, message }`; frontend code expects `{ ok, data, message }` after wrapper conversion.
- Avoid duplicate refresh endpoints when the aggregate overview or mutation response already contains the needed state.
- Prefer path or body parameters consistently. Off-term deletion currently uses query params while similar mutations use request bodies.
- Decide whether `GET /api/courses/{courseId}` should be allowed to create course rows by fetching from `umd.io`; reads with side effects can surprise future caching.
- Keep the guest-session cookie logic in one place. It is currently split between Next pending cookies and Spring persisted guest cookies.
